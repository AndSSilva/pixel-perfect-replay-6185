## Architecture
- All data lives in the Lovable Cloud database (Supabase Postgres) behind RLS; the old local-browser MVP store was removed. Money is integer centavos everywhere; totals are always derived (consumption = delivered/awaiting items of confirmed orders; a sale = a paid comanda; profit = (price - cost) x qty of delivered items that have a cost, items without cost are reported as "lucro parcial", see `src/lib/pedidos/vendas.ts`). Order items snapshot product name/price/cost for history.
- Admin access goes through `authService` (`src/lib/auth/servico.ts`, contract in `tipos.ts`), implemented with Supabase Auth on Lovable Cloud (`servico-supabase.ts`). Access to the panel requires a row in `public.perfis_acesso` with `papel = 'admin'`; `deve_trocar_senha = true` forces `/admin/primeiro-acesso`. The table is read-only for clients (RLS); the flag is cleared only by the `marcar_senha_trocada()` RPC. Fail closed: any failure to confirm the role denies access. Pages guard themselves with `useGuardaAdmin()` (UI barrier); real data protection must come from RLS on every future table. Database structure changes go through Lovable's migration tool (not by hand in `drizzle/`);
- Roles: `perfis_acesso.papel` is `admin` or `master` (one role per user; the DB allows only ONE master via a unique partial index). The master reaches `/master` (company registry: create, edit, activate/deactivate, "Entrar") and can open any company's `/admin`; an admin only sees companies linked in `estabelecimento_membros`. `useGuardaAdmin()` allows admin+master, `useGuardaMaster()` only master; `destinoInicial()` decides where each role lands after login.
- Companies (`estabelecimentos`): `slug` is the public catalog address `/{slug}` (lowercase letters, digits, `-` and `_`, 3-40 chars, immutable, reserved names blocked in the DB and in `src/lib/empresa/slug.ts` - keep both lists equal). Never delete from the app; deactivate (`ativo = false`). Access rule for every future table: use `public.tem_acesso_estabelecimento(estabelecimento_id)` in RLS (master OR linked admin). The company in use in `/admin` is kept per user in localStorage (`src/lib/empresa/atual.ts`); the DB (RLS) is what actually isolates data.
- The tables `estabelecimentos` / `estabelecimento_membros` were created by SQL run directly in the Cloud SQL editor (not Lovable's migration tool), so `types.ts` has them hand-written until Lovable regenerates it from the DB.
- Admin management (`/master/administradores`): creating admins, listing them with e-mail and issuing a new provisional password run in server functions (`src/lib/administradores/administradores.functions.ts` -> `logica.server.ts`). They require a logged-in user (`requireSupabaseAuth`), re-check on the server that the caller is master (`eh_master()` with the caller's token) and only then use the service-role client (`client.server.ts`, loaded dynamically inside the server only). Never import the service-role client from route/component code. Linking/unlinking companies runs in the browser under RLS (master-only policies). A provisional password is generated client-side, shown once, and flags `deve_trocar_senha = true`. `listUsers` is capped at 1000 users; paginate if the platform outgrows that.
- Catalog in the DB (per company): `categorias`, `produtos` (sale price, optional cost price, stock qty, photo path), `mesas` (number only; QR address `/{slug}/mesa_{numero}`). Money is integer centavos; profit is derived (`src/lib/catalogo/calculos.ts`), never stored. Data access lives in `src/lib/catalogo/servico.ts` (react-query keys per company); pages read the company in use via `useEmpresa()` (`EmpresaProvider` in `routes/admin.tsx`). RLS uses `tem_acesso_estabelecimento()`; `eh_membro()` also requires the company to be active. A product's category must belong to the same company (composite FK) and a row cannot change company (trigger). Photos: public bucket `produtos-fotos`, path `{empresa_id}/{produto_id}-{rand}.jpg`, only members of that company can write; the app resizes to JPEG 640px before upload and deletes replaced/removed files (best effort).
- Stock: the physical stock `produtos.estoque_qtd` is NOT writable by clients (column privileges); it changes only through `ajustar_estoque()` (saldo_inicial, reposicao, alteracao_quantidade, baixa_avaria; the last two need a reason) and, in the orders stage, delivery. Every change writes an append-only row in `movimentos_estoque`. Creating a product with initial stock records a `saldo_inicial` movement. SQL source of truth and its test suite (real PostgreSQL) live in `docs/sql/` - run `docs/sql/testes/run.sh` after any SQL change and add a number for each new script.
- Orders in the DB (`docs/sql/08_pedidos.sql`, tests `15_*`/`16_*`): `sessoes_mesa`, `comandas` (one per customer, identified by a secret token stored only as sha256 hash), `pedidos`, `itens_pedido` (snapshot of name/price/cost), `pagamentos`. Clients never write tables: the anonymous customer uses public RPCs (`obter_cardapio_publico`, `identificar_cliente`, `enviar_pedido`, `cancelar_meu_pedido`, `minha_comanda`) and the panel uses authenticated RPCs (`confirmar_pedido`, `rejeitar_pedido`, `entregar_itens/pedido`, `cancelar_item`, `registrar_pagamento`, `excluir_pagamento`, `fechar_comanda`, `iniciar_fechamento_mesa`, `retomar_atendimento_mesa`, `liberar_mesa`); the panel only SELECTs (never select `comandas.token_hash`: list columns, see `COLUNAS_COMANDA`). Rules: pending order expires in 45 min and reserves availability (stock minus reserved); physical stock drops only on delivery (all-or-nothing, refused if short); cancelling an item needs a reason, releases the reservation and leaves the bill; flag `inativar_ao_zerar_estoque` ON limits the customer to the available quantity and inactivates the product at zero, OFF lets customers order anyway. Code: `src/lib/pedidos/` (`servico-cliente`, `servico-painel`, `carrinho`, `painel`, `tipos` with error codes = the DB exception messages), customer page `src/routes/$slug.$mesa.tsx` (`/{slug}/mesa_{n}`, token in localStorage `mesa-digital:comanda:{slug}:{n}`, company colors via `corSegura`), panel `src/routes/admin.pedidos.tsx` (polling every 10 s).
- Bills and tables in the DB: `/admin/contas` (open comandas of tables in service), `/admin/contas/$contaId` (items, payments with change, close) and `/admin/mesas/$mesaId` (start closing, resume, release) use `src/lib/pedidos/contas.ts` (pure rules mirroring the DB checks: `impedimentoParaFechar`, `impedimentoParaLiberar`, `validarPagamento`) and the RPCs in `servico-painel.ts`; after any action call `atualizarAtendimento(qc, empresaId)`. The DB always re-validates. A table's status comes from `sessoes_mesa` (livre / ocupada / em fechamento).
- Cash register (`docs/sql/09_caixa.sql`, tests `17_caixa.sql`): one open `caixas` row per company (partial unique index); `registrar_pagamento` requires it (error `caixa_fechado`) and stamps `pagamentos.caixa_id`; `excluir_pagamento` is refused once that caixa is closed (`caixa_ja_fechado`). Expected cash = opening + cash payments (change never counts) + reforços - sangrias (`caixa_esperado`, single source: RPC `resumo_caixa`). `fechar_caixa` stores esperado, contado and diferenca (contado - esperado). Sangria cannot exceed the expected cash. UI: `/admin/contas/caixa`; payments form is disabled when no caixa is open. Code in `src/lib/pedidos/caixa.ts` and `servico-painel.ts`.
- Dashboard, sales history (`/admin/historico`, by paid comanda, period capped at 500 accounts) and settings (read-only company data; identity edit is not built yet) come from the DB. Customer-facing menu is `/{slug}/mesa_{n}` only.
- Brand: INOV4 HUB identity for admin/master (tokens in `src/styles.css`, logos in `public/brand/`, `BrandLogo`). Theme is automatic by device clock (light 06:00-17:59 / dark 18:00-05:59); a single button (`ThemeToggle`) offers the opposite theme, and a manual switch lasts only until the next 06:00/18:00 turn (`src/lib/tema.ts`). The `dark` class lives on `<html>`.
- First access: admins start with a provisional password and must set their own at `/admin/primeiro-acesso` (flag `deveTrocarSenha` in the session).
